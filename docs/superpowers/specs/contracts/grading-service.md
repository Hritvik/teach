# Shared grading and key-verification service

Status: concrete implementation design, 2026-10-26; no provider calls or paid tests performed.
Authority: [accepted integration contract](../../../../.scratch/teach-general/artifacts/integration-and-dependency-contract.md).
The learner approved shared independent grading and the initial US$5/month Teach inference cap on
2026-10-26. The cap is 5,000,000 micro-USD per learner-local calendar month. Approval completes the
planning decision; deployment, credential setup and live paid tests remain separately gated.

## Provider and invocation

Initial technical model selection: OpenAI Responses with snapshot `gpt-5.4-mini-2026-03-17`, not the floating alias. The current model
page documents Responses, Structured Outputs, `reasoning.effort: none`, a 400,000-token context and
US$0.75/M input plus US$4.50/M output. These are the researched rates, not future price guarantees.
The learner has not selected this provider or authorised its cost. The existing MyFitnessGuide setup
is a hosting/authentication precedent, not evidence of an existing hosted model-grading integration.
Use ordinary global processing for this candidate; selecting a regional processing endpoint requires its uplift in the
price policy. [Model and rates](https://developers.openai.com/api/docs/models/gpt-5.4-mini)

One stateless request per physical invocation: `model` above, `reasoning:{effort:"none"}`, `store:false`,
`background:false`, `max_output_tokens:2048`, `tools:[]`, no previous response/conversation reference,
and `text.format:{type:"json_schema",name:<purpose-version>,strict:true,schema:<pinned schema>}`.
Use no SDK automatic retries. Pin the SDK version and the prompt/schema hash in the lockfile/release.
Strict schema constrains shape, not factual correctness; refusals/incomplete outputs require explicit
handling. [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)

No model web search, file upload, embeddings, hosted tools or automatic provider/model fallback is
selected. The grader is an internal Worker module invocation, not a public `/grade` route or another
learner store. Only the job orchestrator can invoke it; it has no MCP/SQL/control tools. The provider
key is a Worker secret, never supplied to a client or included in the model input.

## Isolation and source authority

The tutor/item-writer cannot certify its own key by posting `verified:true`. A key-verification job
consumes immutable source captures created by the trusted source-fetch/anchor adapter. That adapter,
not the model, fetches the named public passage or code bytes, records hash/version/location, and applies
fetch/SSRF/size policy. Unreachable, changed or unsupported captures hold the key. Every key point must
have at least one trusted capture supporting it. A model's invented citation is never a capture.
Item content versions remain immutable. Verification completion appends an `item_verifications` record
and advances the item's current-verification projection; it never rewrites content or increments the
item version merely to say verification succeeded. A changed capture or verifier prompt can recheck the
same content version; changing the stem, key, rubric or exact-key content creates a new content version.

Verification and grading use separate jobs, role instructions, context and output schemas. Neither
invocation receives the authoring conversation, learner mastery, previous grader verdict or an agent's
claimed correct answer. A regrade receives the same item/key and answer, not the original grade or
unrelated conversation. Shared model family does not mean shared conversational context.

Treat answer, quoted sources and item prose as untrusted data, never executable instructions. Fixed
developer instructions say to evaluate only against supplied rubric/captures and to refuse unsupported
judgements; data is JSON-encoded in a separate user message. No embedded request can add tools, change
schemas, grant permissions or award mastery. Confidence/hint history stays out of the content grader;
the tracker separately derives credited strength from that metadata.

## Internal request contract

All objects reject additional fields. IDs are opaque strings; versions are positive integers; hashes
are SHA-256 hex. Runtime limits apply before queueing and again before dispatch; never truncate a key
or learner answer silently. The assembled model input is text-only, at most 32 KiB UTF-8, including
instructions, schemas and data; an oversized job stays pending with `input_too_large`.

`ModelJobRequestV1` fields (all required):

| Field | Type and rule |
|---|---|
| `job_id`, `dispatch_id` | Logical job id and unique physical-call id; generated by orchestrator |
| `purpose` | `key_verify` / `grade` / `regrade` |
| `attempt_id` | string for grade/regrade, null for key_verify |
| `item_id`, `item_version`, `key_version` | Existing immutable item/key content version; v1 key_version=item_version |
| `verification_id` | Accepted append-only verification record for grade/regrade; null for key_verify |
| `protocol_version`, `rules_version`, `prompt_version` | Pinned compatible versions |
| `recovery_generation`, `job_revision` | Security/recovery and job CAS fences |
| `item` | `{stem:string,level:1|2|3|4,essential_context:string}` |
| `key_points` | 1–16 `{point_id:string,criterion:string,required:boolean,anchor_ids:string[]}` |
| `captures` | `{anchor_id:string,capture_hash:string,passage:string}[]` tied to current verification |
| `answer` | Learner's exact answer string for grade/regrade; null for key_verify |
| `exact_key` | Immutable hidden deterministic-key object for key_verify, null for free-text grade/regrade; shape from data contract |

The provider receives only `purpose`, `item`, `key_points`, `captures`, `answer` and the purpose-appropriate
`exact_key`, plus the fixed
purpose-specific instructions. Internal identities, learner account, grants, session transcript,
security fences and billing metadata are not model context. `essential_context` is the problem's
necessary factual setup, not a hidden transcript summary.

## Model result contracts

Strict output schema `KeyVerificationV1`: `{points:[{point_id:string,verdict:"supported"|"unsupported"|
"uncertain",anchor_ids:string[],reason:string}],exact_key_verdict:"supported"|"unsupported"|"uncertain"|null,
exact_key_point_ids:string[],exact_key_reason:string|null}`. All fields required; root and children disallow extra
properties. Runtime requires every submitted point exactly once, known anchor ids only and a reason
of at most 500 characters. Accept verification only when every point is supported and its captures
remain valid. If the item has an exact key, require `exact_key_verdict=supported`, its cited point ids
to be known supported points, and a reason explaining why the precise hidden expected value follows
from the captured sources/problem. Merely verifying generic prose about the concept is insufficient.
For a free-text item require null exact-key verdict/reason and no exact-key point ids. Unsupported,
uncertain or inconsistent exact-key results hold the item even if every generic point is supported.
Append the complete per-point and exact-key verdict/provenance
to `item_verifications`; update `items.current_verification_id` only through the tracker-owned projection.
A stale/failed capture or verification invalidation holds the item without mutating its content or
erasing earlier verification history. Verification never grades a learner answer.

Strict output schema `ContentGradeV1`: `{status:"graded"|"ungradable",grade:"correct"|"partial"|"wrong"|
null,points:[{point_id:string,result:"met"|"partial"|"missed"|"unassessable",reason:string}],
feedback:string,misconception_hypothesis:string|null,probe_warranted:boolean}`. All fields required,
no extra properties; all point ids exactly once; reasons at most 500 characters and feedback at most
1,500. `ungradable` requires null grade. Runtime derives the aggregate from required points: any unassessable point yields ungradable/null;
all met yields correct; otherwise at least one met/partial yields partial, and none yields wrong.
The model aggregate must match or the result is rejected. A rubric must encode any disqualifying
contradiction as a required criterion; optional details cannot silently change the rule.

The hidden exact key is never included in the learner-facing item payload before their attempt or
returned by a public verification-status endpoint. The verifier can inspect it in isolation; exact-key
answer evaluation remains tracker-owned and deterministic, using only a verified content snapshot.

The grading model returns content assessment only. The tracker computes credited strength/mastery, attaches
trusted ids/versions and grade provenance, and validates/commits the result with the accepted attempt
contract. Grader uncertainty, refusal, malformed output or transport failure never becomes wrong.
Do not store hidden reasoning; keep concise criterion reasons and feedback necessary for audit.

## Job lifecycle and duplicate prevention

Keep jobs/results in LEARNING_DB, with one logical normal grade per `(attempt_id,key_version)` and
one key verification per `(item_id,key_version,capture_set_hash,prompt_version)`. Regrading requires a
recorded dispute and unique dispute revision. Statuses: `queued`, `running`, `pending`, `succeeded`,
`cancelled`, `superseded`; `pending_reason` identifies budget/auth/source/provider/review requirements.

Persist `grade_jobs(job_id PK,identity_hash UNIQUE,purpose,attempt_id?,item_id,item_version,
key_version,verification_id?,capture_set_hash,protocol_version,rules_version,prompt_version,model_snapshot,
recovery_generation,job_revision,status,pending_reason?,dispatch_id?,lease_until?,physical_call_count,
result_json?,created_at,updated_at)`. For v1 `key_version` equals `item_version`: changing any key,
rubric or stem produces a new immutable item version, not an independent mutable key. Verification
status is append-only metadata separate from content and does not itself increment item/key version.
A verification identity hashes the complete assessment content: stem, essential context, key points,
distractors, assessment form and hidden exact-key object, plus capture-set and verifier-prompt hashes.
`result_json` is the validated structured result plus trusted provider/prompt/version provenance.
A completed verification job appends an `item_verifications` record keyed by item version, capture-set
hash and verifier prompt, with its trusted completion sequence; rechecks do not create an endless
content-version/verification cycle. Failed or superseded verification cannot make an item eligible.

Job `succeeded` transitions the attempt to `graded`; a pending job leaves the attempt `pending`;
cancelled/superseded terminal work leaves `ungraded` unless a still-valid accepted result already
exists. A regrade amends a disputed attempt under its current revision, never creates another learning
attempt. All finalisation batches carry SecurityLedger admission and recovery-generation guards.

MCP `answer` persists the learner answer and job atomically, returning attempt/job id plus `pending`.
`attempt_status(attempt_id)` reads the same job/result; it does not enqueue another grade. The
internal scheduled runner claims at most one job at a time with a CAS dispatch nonce/lease. Repeated
queue delivery, polls or lease expiry cannot create a second accepted evidence record.

Before dispatch: for grade/regrade validate the pinned accepted verification record and current
item eligibility, along with live key/captures, grant/capability and SecurityLedger recovery generation;
claim job revision, reserve cost, then mark the dispatch admitted. No external model call is inside a
D1/DO transaction. On return, validate again: current recovery generation, deletion status, immutable
key/capture validity, pinned verification acceptance, current eligibility and job CAS nonce. Commit one result/evidence/scheduling transition atomically.
A superseded/deleted/cancelled job discards content, but still reconciles its cost.

A response timeout means the physical call may have been charged. Keep its reservation and mark the
attempt pending; do not automatically repeat an ambiguous call. A later explicit retry is a new
`dispatch_id`, with another reservation, on the same logical job/attempt. Maximum two physical calls
per job (including a retry); then require learner-visible review. A dispute creates one fresh regrade
job; further disagreement stays unresolved until a human/source correction, not an invisible retry loop.

For an explicit transient rejection before inference, permit one retry after at least 30 seconds with
its own reservation; retain the first charge unless provider usage or reliable billing reconciliation
proves no cost. For refusal, schema failure or token-limit completion, hold for review rather than
blindly retrying. Local timeout is 45 seconds. Never assume cancelling local fetch cancels provider
billing; cancel marks the job, blocks acceptance and conservatively retains unsettled cost.

No raw payload is needed in a scheduled queue message: it carries only job id/generation. The database
is authoritative; scheduled dispatch or delivery merely wakes the runner. Restored jobs cannot reuse
old dispatch authority or budget reservations; SecurityLedger fences and explicit reconciliation apply.

## Hard application budget

Use SecurityLedger's synchronous transaction for reservation/settlement, outside learning backups.
Money is integer micro-USD. `budget_policy` pins cap, period, snapshot, processing region and price
version; calendar months use the learner timezone. The approved initial cap is 5,000,000 micro-USD (US$5/month).
Reserve verification, initial grading, regrading and retries from the same cap; no hidden verifier budget.

With no tools and the selected bounds, reserve the conservative entire 400,000-token input capacity
plus 2,048 output tokens per physical call: `ceil(400000*0.75 + 2048*4.50) = 309216` micro-USD.
Use uncached input rates even if caching discounts may occur. This intentionally over-reserves;
settle confirmed usage at `ceil(input_tokens*0.75 + output_tokens*4.50)` micro-USD, releasing the
remainder only on trustworthy usage. Unknown outcomes retain the full reservation for the period.
An invoice discrepancy suspends dispatch and keeps the higher known cost, never releases disputed cost.

Atomically admit only if `settled + outstanding + new_reservation <= cap`. Reserve before the network
request; deny concurrent/replayed reservations by `dispatch_id`. At exhaustion keep answers pending,
show balance/reason and require a trusted learner control to change the cap. A cap change never
retroactively authorises previous calls. A month boundary does not erase unresolved reservations from
calls admitted in the prior month; attribution follows the admission period even if settlement is later.

The guarantee is a hard cap on Teach-admitted inference liability under the verified rate/limits,
not a guarantee about taxes, FX, Cloudflare hosting, unrelated API use or unannounced provider repricing.
Use a dedicated API project/key and disable paid dispatch when model, price policy, billing mode or
upper bound cannot be verified. Pin a rate policy at deployment; recheck before enabling a new month,
a model/endpoint change or any price notice. Provider prices can change, so an unconditional dollar
invoice cap cannot be proven by application bookkeeping alone; disclose this bound in budget approval.
Do not rely on a provider dashboard's budget alert as the hard enforcement mechanism.

## Privacy and retained data

Send only general-learning problem/key/capture excerpts and the answer; no employer content, personal
profile, token, full session or unrelated progress. Strip private account identifiers from provider
metadata and redact payloads from application/error logs. Provider request ids and usage totals may
be retained for cost audit; encrypt model-job payloads under the learning-data controls and delete
subject-linked content when the learner deletes it, including pending inputs and feedback.

`store:false` avoids retained Responses application state for this stateless path; it does **not**
mean zero provider retention. OpenAI documents abuse-monitoring content retention up to 30 days, with
exceptions, and separate eligibility for Zero Data Retention. Do not claim access to ZDR or promise
Teach deletion can remove provider logs. These limits must be disclosed before live inference.
[OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data)

## Release evidence

- Validate every key point against trusted captures; reject forged verification and invented anchors.
- Prove successful/repeated verification appends metadata without changing content versions; stale
  verification holds eligibility and cannot accidentally trigger an endless new-version/recheck cycle.
- Evaluate injection, ambiguous keys, correct/partial/wrong answers and legitimate novel formulations
  on a human-reviewed fixed corpus; require zero unsupported-key acceptance and all safety invariants.
- Prove identical physical-call retries cannot duplicate evidence; uncertain costs remain reserved.
- Prove parallel admission, month rollover and restored D1 cannot bypass the cap/security fences.
- Test refusal, truncated output, malformed schema, provider outage and disputed grades as pending.
- Confirm actual API entitlement, snapshot availability and current rates before any paid call.
- Complete source-verification + free-text assessment + resume on every selected launch client.

No credential, paid invocation, provider account, deployment or model-quality result was created here.
