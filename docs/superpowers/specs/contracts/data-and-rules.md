# Learning data and rules contract

Status: technical planning decision, 2026-10-26; no migrations or runtime tests have been executed.
This refines the [current design](../2026-10-23-teach-design.md), [glossary](../../../../GLOSSARY.md),
[state/write](../../../../.scratch/teach-general/artifacts/state-and-write-contract.md) and
[assessment](../../../../.scratch/teach-general/artifacts/assessment-and-review-contract.md) contracts.
Learner-confirmed behaviour wins over implementation details here; identified corrections must be reconciled before build.

## 1. Types, ownership and version boundaries

Use one active D1 learning database, exposed to handlers as the admitted `LEARNING_DB` slot.
The security contract provisions A/B slots for isolated recovery; the inactive slot is maintenance-only,
not a second tracker. SecurityLedger owns non-rollback security state. IDs are opaque `<prefix>_<UUIDv4>` generated by the server, except client-generated
UUID request/attempt identities. Store instants as UTC ISO-8601 milliseconds, levels as integers 1–4,
versions/revisions as positive integers and booleans as 0/1. IANA learner timezone starts `Asia/Kolkata`.
Save the timezone name and derived local calendar date on each observation; later timezone changes
never rewrite old evidence dates. Observations may carry an earlier `occurred_at`, but the server records
`received_at` and an immutable global `seq`; clients cannot choose commit order or promote backfilled
unverified work into assessed evidence. Reject future `occurred_at` more than five minutes ahead of server time.

`protocol_version=1` defines tool schemas; `rules_version=1` defines mastery/scheduling; `schema_version`
tracks forward-only migrations. Each operation explicitly names supported protocol/rules versions.
Reject incompatible versions before any writes. Derived outputs include `projection_revision` and
`as_of_seq`. Store historical rule definitions and scheduler manifests so replay never depends on today's
package defaults. Deployment pins exact npm dependencies/lockfile and scheduler engine build hash.

## 2. Schema layout and constraints

The following are concrete field layouts, not a request to invent a second document later. All entity
IDs are TEXT primary keys. `JSON` denotes validated JSON text. Mutable entities carry `version`,
`created_seq`, `updated_seq`; all learner data has `learner_id` and validates references belong to it.
Foreign keys use RESTRICT, not destructive cascading that erases assessment history. Explicit deletion
uses the privacy contract. CHECK constraints enforce enums, versions, levels and numeric bounds.

## 3. Atomic mutation and response contract

All ordinary mutating paths, including item verification publication, lease claims, grading finalisation
and corrections, enter through SecurityLedger admission. A client-supplied generation must match current admission;
a stale generation is refused, never silently rewritten on retry. `meta.generation` and `write_enabled`
are tested inside every D1 mutation batch against that server-admitted generation. The security
contract defines pause/fence/cutover; no background task bypasses the ordinary guard merely by being
internal. Private maintenance is a distinct authority: SecurityLedger-issued `{operation_id,slot,
generation,phase,expected_meta_revision}` permits only the recorded fence/import/migrate/replay/purge/
activate step for that slot while ordinary writes are disabled. The maintenance batch compares those
values and allowed phase against meta/maintenance checkpoint; it cannot reuse the ordinary
write_enabled=1 precondition when its purpose is fencing or recovery. No MCP scope or caller boolean
grants this authority. Append private checkpoints after each idempotent step; mismatched/unknown
operation, slot, generation or phase fails closed.

A read validates current security admission and uses the active database generation, returning its
projection revision. Use primary-consistent reads for mutation preparation; never mix a stale read
replica with an assumed current version. Version conditions remain necessary even after primary reads.

A batch first conditionally inserts a unique write guard only if recovery generation, schema/rules,
all expected entity/correction/graph/projection revisions, and validation predicates hold. Every
subsequent mutation is conditioned on that guard. Insert the receipt/event/projections and mark guard
consumed in the same batch. A missing guard means no effects; return a typed conflict from batch reads.
A SQL error rolls back the batch. Graph/correction replay may be computed before batching, but its
source revision is compared inside the guard; on conflict recompute, never apply stale projections.
No model/network side effect occurs while computing or retrying a D1 atomic batch.

The public tool write envelope is closed (reject unknown fields):

```json
{"protocol_version":1,"rules_version":1,"recovery_generation":4,
 "request_id":"UUID","operation":"set_aim","session_id":"s_UUID",
 "reason":"Learner accepted the aim","expected":{"ai_UUID":2},
 "data":{"concept_id":"c_UUID","owner_kind":"learner","owner_id":"l_UUID","level":3,"parked":false}}
```

Authenticated learner/connection are never caller-selected. Maximum body is 64 KiB; learner answer
16 KiB, reason 1 KiB and generic text field 16 KiB UTF-8. Pagination defaults 25/max 100. Canonical
semantic SHA-256 covers operation/version/generation/expected/data/session/reason, excluding transport
trace ids and insignificant JSON key order. Same request id/hash returns its original result; changed
hash returns `IDEMPOTENCY_MISMATCH`. Receipts remain until explicit privacy deletion or generation
retirement. A generation change caused by restore, deletion or maintenance returns STALE_GENERATION
for old envelopes; a fresh admission must not silently upgrade them. Private deleted receipt data is purged and
must not be returned as replayed content. Retain only the minimal deletion-safe refusal identity.

```json
{"ok":true,"data":{"ids":["ai_UUID"],"versions":{"ai_UUID":3}},
 "meta":{"request_id":"UUID","recovery_generation":4,"as_of_seq":81,
 "rules_version":1,"projection_revision":15,"replayed":false}}
```

Failures use `{"ok":false,"error":{"code":"VERSION_CONFLICT","message":"...",
"retryable":false,"current_versions":{"ai_UUID":3}},"meta":{"request_id":"UUID"}}`.
Codes are `INVALID_INPUT`, `UNAUTHORISED`, `FORBIDDEN`, `INCOMPATIBLE_VERSION`, `STALE_GENERATION`,
`VERSION_CONFLICT`, `IDEMPOTENCY_MISMATCH`, `ITEM_HELD`, `REVIEW_LEASE_CONFLICT`, `MAINTENANCE`,
`DEPENDENCY_UNAVAILABLE`, `BUDGET_EXHAUSTED`. Transient dependency/maintenance errors may be retried
with the same identity after backoff; forbidden/invalid/version conflicts require intervention or a
fresh approved operation, not retrying a changed payload under the same key. Poll/status reads do not
create records. MCP protocol framing errors remain transport errors; domain failures use this envelope.

`item_next` is a mutation despite its name and uses a request envelope. Separate internal key access
requires verifier/grader authority: a tutor must not fetch and leak a withheld key before the attempt.
Verification provenance is a validated trusted-service assertion, not permission created by an agent
label. Throughline/reader/book tooling remains namespaced and disabled until its phase.

### Exact-key item and answer schemas

The v1 exact evaluator supports only single-choice `mcq_single` and `predict_scalar`; other predictions,
traces and prose/design answers use the shared grader. A verified exact key is private item-version
content, omitted from `item_next` and all learner/tutor reads until feedback is released.

- `mcq_single` content: `{kind:"mcq_single", options:[{option_id:string,label:string}], correct_option_id:string}`.
  Require 2–6 options, unique case-sensitive ids of 1–64 ASCII letters/digits/underscore/hyphen, exactly one
  correct id and matching verified source point. Visible item exposes options, not correct_option_id.
  Answer is exactly `{kind:"mcq_single",option_id:string}`. Unknown ids or extra fields are INVALID_INPUT;
  correct id yields correct, any other listed id yields wrong. No partial-credit answer exists.
- `predict_scalar` content: `{kind:"predict_scalar",expected:string|number|boolean|null}`. The visible
  stem states what scalar is requested. Answer is `{kind:"predict_scalar",value:string|number|boolean|null}`.
  Equality is type-strict: no string-to-number/boolean coercion. Strings compare exact Unicode code-point
  sequences, case and whitespace included, with no trim/normalisation. Numbers compare finite ECMAScript
  Number values (`-0` equals `0`, `1` equals `1.0`); require safe integers when integer-valued. NaN,
  Infinity, arrays, objects and unsafe integers are INVALID_INPUT. There is no tolerance or automatic
  rounding; an item needing either must state a canonical string output or use free-text grading.
  Equal yields correct; unequal yields wrong; no partial exact grade. Source verification holds ambiguous keys; the trusted KeyVerificationV1 result must explicitly support
  the precise hidden expected value, not merely related rubric points.
- Free-text answer is `{kind:"free_text",text:string}` within the 16 KiB limit. For all kinds the outer
  `answer` operation pins attempt_id, immutable item_version, confidence/help and optional review lease.
  Submitted kind must match the issued item. Changing the submitted answer after acceptance is a new
  attempt; reusing the attempt with changed content refuses rather than replacing its first answer.

Set mcq_single `assessment_form=recognition`. A correct recognition response may be practice/exposure
but cannot establish production Recall, Mechanism, Purpose or Transfer credit, even with sure confidence.
A predict_scalar can be `production` only where the verified rubric genuinely elicits that level; one
number cannot prove a design explanation or Transfer. Deterministic correctness does not imply that
an item validly tests the claimed learning depth. Validate this during source/rubric publication.

### Amendment, retraction and publication authority

All replacement objects are closed schemas; fields not listed below refuse, rather than being ignored.
`teach:read` cannot mutate. `teach:learn` and `teach:organize` are granted capabilities, not proof of a
human actor; target ownership, current effective revision and generation are still checked.

| Authority / operation | Allowed fields or effect | Forbidden shortcut |
|---|---|---|
| `teach:learn` amend own session observation | inquiry/answer-explanation text; confidence and help metadata; session exit-ticket wording/muddiest point/what_helped | Cannot rewrite an accepted assessment answer, observed time/day, item identity or grade; changed answer requires new attempt |
| `teach:organize` amend descriptive records | concept title/purpose/realm/area/slug, learner-note text, goal title/source/urgency/due date, validated links/aim edits through their typed operations | No mastery/projection/grade, record reassignment, merge confirmation, identity or provenance edits |
| Ordinary `retract` | mark own unassessed inquiry/exposure observation withdrawn with reason; never physically delete private content as a pretend purge | Cannot remove a wrong/partial/graded attempt to inflate progress; use dispute/control exclusion |
| `teach:learn` dispute | append disputed state/reason against an attempt effective revision; existing provisional/regrade rules apply | Cannot supply replacement grade or label an attempt correct |
| Trusted shared grader completion/regrade | validated content grade and point results from the pinned key/captures; tracker computes strength and projections | External client assertions of grader/model name or signature-free result are not authority |
| Trusted learner control | approve a merge; exclude/retract an assessed record with explicit bound confirmation and audit reason, triggering replay/provisional notice | Exclusion is not a correct answer, new strong day or certified replacement performance |
| Trusted verifier service | append item_verifications using validated per-point source verdicts and job provenance | Tutor `item_verify` queues work; it cannot submit its own supported=true certification |

Only the tracker generates `content_grade` for exact keys, evidence `strength`, `as_of_seq`, projection
fields and trusted provenance. Ordinary amendment/retract operations cannot set any of those, change
`item_id/item_version`, relabel another session's evidence, or erase correction history. Confidence/help
amendments recompute strength without modifying the content grade; their provenance remains caller-
reported. Restored/deleted content is governed by security maintenance, not this amendment API.

`item_versions` never change for a verification-only recheck. Every check appends an item_verifications
record keyed by the same item_version plus source capture hash and verifier prompt version; publication
selects the latest applicable valid trusted check and can hold an item after an invalidating source event.
A key/stem/context/assessment_form/options/expected-value/rubric change creates a new item_version.
For v1 key_version is exactly item_version. Verification evidence changes alone never masquerade as a
new question or erase the original check. KeyVerificationV1 must bind the complete content hash including hidden exact_key, return an explicit
exact_key verdict with supporting known point ids, and support its precise correct option/scalar before
publication. Generic key-point support alone cannot certify an arbitrary hidden value. Historical
attempts retain the item/key and verification ids actually used. Concurrent publication compares current version and publication revision atomically.

## 5. Deterministic evidence and mastery rules

Technical interpretation of confirmed rules: content-correct helped/guess answers are practice,
not a false direct failure. They never create strong-correct credit, and neither assistance nor missing
confidence alone demotes demonstrated understanding. A genuinely wrong or content-partial assessed
answer is a miss. Store both content grade and credited strength to avoid conflating these cases.

For each concept/level, resolve corrections against their root records using accepted effective-revision
chains; exclude retractions and disputed attempts. Replay resulting observations by `(occurred_at, seq)`;
`seq` breaks ties and defines immutable acceptance order for concurrent corrections. Backfilled events
may therefore change historical ordering but only through a new version-checked projection revision.
Use the source event's saved local date for two-day credit, not its later regrade/receipt date.

1. No effective exposure/evidence: Unknown. Exposure, inquiry or practice-only: Exposed if no stronger state.
2. A genuine miss clears the post-miss strong-day set and yields Shaky until another strong correct.
3. A strong correct requires a production-form item valid for the assessed level and adds its original local day. One distinct post-miss day yields Solid; two yield Secure.
4. Further correct practice, exposure, unknown confidence or inferred lower-level support leaves the
   demonstrated state unchanged. Same-day repetitions cannot manufacture a second independent day.
5. A material dispute marks the affected projection provisional and prevents certified readiness; replay
   without that attempt. Resolution is a correction, not a second performance or another review rating.
6. No implicit lower-level miss exists. Higher-level support is labelled inferred and can establish at
   most exposure where no direct evidence exists; it cannot demote or satisfy a required lower-level aim.
7. Stale follows changed source evidence, not mere relocation. Fading means overdue duration greater
   than twice the last interval; neither flag changes mastery. Provisional readiness is never shown as final.

Effective aim is the highest unparked aim among active owners (retained v1 technical default). Keep each
owner's aim, even after merge. Requires edges point dependent → prerequisite. Deepens follows the original logical-clocks →
vector-clocks example: foundation → advanced; it implies `requires(advanced, foundation)`, not the
same-direction requires edge. Normalise both into dependent → prerequisite for cycle checking. A concept is on the
frontier when it has an unmet unparked aim and each prerequisite is at least Solid at Mechanism.
Requires at Mechanism is the specified prerequisite depth; Solid is the v1 evidence threshold. Goals
show count met / count total active aims, not a fabricated average score. Preserve the existing v1
priority weights, 70/30 balance, 60-day archive and 21-day urgency reconfirmation as rules_v1
technical defaults, not newly confirmed learner preferences. The implementation may expose these
through versioned rule updates, not unrestricted per-request hidden knobs.

Pin the remaining priority terms: aim weight Recall/Mechanism=1, Purpose=2, Transfer=3; urgent factor
4 when overdue, 3 when due within 7 days, 2 within 21 days, otherwise 1 (including undated urgent goals).
Growth interest is 1 for an active aim, plus 1 for a learner inquiry in the preceding 30 days. For an
unmet target, gap is `max(1, aim_level - highest_direct_Solid_or_Secure_level_below_aim)`, with absent
lower evidence equal to 0; an already-met target is excluded rather than assigned positive gap.
Apply the original `gap × slot_weight × (1 + .25 × directly_unblocked_concepts) + 2 × open_misconception
+ 1 × stale` formula; tie-break by earliest aim creation seq then concept id. Snapshot evaluation time
in the response. This keeps a demonstrated higher level from zeroing an unmet lower-level aim.

## 6. Scheduling and review occurrence rules

Use a scheduler adapter `initialise(card_id, at, manifest)` and `review(card, rating, at, manifest)`;
inputs/outputs are immutable JSON with the engine's complete card/review-log state. The official
[ts-fsrs documentation](https://open-spaced-repetition.github.io/ts-fsrs/) exposes four ratings and
configurable retention; pin the actual package and chosen engine version/build at scaffold rather than
copy an obsolete example API. Technical v1 choice: FSRS-7 engine, fixed desired retention 0.90, no random fuzzing,
maximum interval 36,500 days, scheduler default parameters copied into the immutable manifest.

| Effective assessment | Rating / action |
|---|---|
| Strong correct (correct, independent, sure/think) | Good; first such answer creates the concept/level schedule |
| Genuine wrong or content-partial answer | Again if schedule exists; before Solid record miss with no memory schedule |
| Correct helped answer, correct guess or correct recognition-only item | Hard only if schedule exists; practice cannot initialise demonstrated mastery |
| Correct with unknown confidence | No scheduler rating; preserve answer and unresolved strength, never Again |
| Exposure/inquiry/self-rating/skipped/expired/disputed | No rating; disputes trigger replay without that attempt |

Do not use Easy in rules_v1: confidence alone is insufficient evidence for it. A rating change after
regrade replays the original attempt once at its original scheduler time; unrelated later observations
remain. FSRS rating and mastery state serve different purposes; Hard practice may schedule review but
cannot produce Solid/Secure. No hidden optimisation or new weights are learned automatically in v1.

A due concept/level owns one active review occurrence. `item_next` atomically leases it for 10 minutes,
with increasing lease generation and schedule/projection revision. Explicit takeover invalidates the old
lease; expiry alone does not mark failure. Answer submission consumes it once. The current eligible
attempt alone applies the scheduler transition. A late old-lease answer may remain valid evidence, but
is marked non-scheduling and cannot create extra independent-day credit solely from reissued material.
Pending grading keeps the occurrence awaiting its attempt; a later takeover fences the old job result
from schedule advancement but does not fabricate a wrong grade.

For an accepted answer with unknown confidence, consume the occurrence and advance its coordination
revision without changing FSRS state. Suppress that unchanged due review for the current session;
it becomes eligible again in another session using a different item. A later confidence amendment can
rate the original attempt via replay; it is not a new answer. Scheduler time is the original server
accepted observation time, never the grader completion time; replay clamps each time to at least the
previous rating time. Genuine backfilled unverified work does not retroactively seed an FSRS review.

## 7. Merge, closure and correction transactions

A merge validates confirmed source/target versions, canonicalises redirects, checks graph constraints
and graph revision, then atomically writes redirect/link coalescing, reassigns active references while
retaining original evidence identity, and recomputes affected projections. Parallel edges coalesce;
new self edges drop with explicit merge provenance; a new prerequisite cycle refuses the merge.
If the same owner has aims on both concepts, retain both original aim ids/history with one canonical
effective owner aim at max level; parked is true only when all of that owner's merged aims were parked.
Do not lower another owner's aim. Corrections continue addressing original record ids through redirects.

Goal closure requires one keep/lower/drop decision for every owned aim. Lower cannot exceed its old
level. Keep/lower transfer ownership to learner; coalesce with existing learner aim using max level,
retaining originals in history. Drop retracts the goal-owned aim without deleting evidence. The goal
state and all aim decisions commit under one guard; new aims added since preview produce conflict.

A grade correction requires the trusted shared-grader regrade result, original item/key version and
effective revision. The ordinary amend/retract path cannot alter grades or turn a learner objection into
a correct answer. Changing an item key creates a new immutable version and append-only verification,
never an edit to the original attempt's key. Rebuild affected
mastery/schedules then invalidate obsolete review leases atomically. Content deletion is an explicit
privacy operation under the security/recovery contract, not a history-preserving retraction.

Deletion uses the full mutation barrier, not only a tombstone check before admission: SecurityLedger
records the deletion decision, enters deletion mode and increments generation; the private maintenance
path fences D1 writes off at that generation before purging targets, private dependants, receipts and
pending jobs. An old admitted batch either commits before the fence and is included in the purge, or
fails its old-generation guard after the fence. Complete the purge/checkpoint, then re-enable only the
ledger-selected slot/generation and acknowledge deletion. All stale envelopes and old-generation grader
completions refuse as STALE_GENERATION. Preserve the deletion ledger outside learning rollback so
restore reapplies it; generation fencing also prevents delayed writes from recreating deleted content.

## 8. Required build checks

Test D1 guard contention, every batch statement's fence, failure rollback and receipt replay; direct
attempt double submission under different request ids; entity and correction races; independent-day
credit under help/unknown confidence/timezone changes; deterministic dispute replay; schedule lease
expiry/takeover and late grader completion; merge cycles/coalescing and goal closure races. Exercise a
real remote D1 environment with approval before claiming batch parity. Unit, integration and critical
client E2E checks must pass with at least 80% measured coverage; mocks do not certify remote semantics.

[D1 binding documentation](https://developers.cloudflare.com/d1/worker-api/d1-database/) documents
prepared statements and sequential atomic batches with rollback on failure. The conditional guard,
projection replay and graph coalescing above are Teach design decisions requiring tests, not claims
that the provider implements those business rules automatically.
